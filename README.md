# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 실행 방법
```
gcc -O2 -fno-optimize-sibling-calls -o sort_compare sort_compare.c
./sort_compare
```
`-fno-optimize-sibling-calls`는 컴파일러가 퀵 정렬의 두 번째 재귀 호출을 반복문으로 바꿔 재귀 스택 사용량이 줄어드는 것을 막기 위한 옵션입니다.

## 구현 및 측정 방법
- 데이터: 0 ~ 999,999 범위의 무작위 정수(중복 허용), n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 각 n에서 다섯 알고리즘(힙, 병합, 퀵 First/Random/Median-of-Three)은 같은 원본의 복사본을 사용하고, 정렬 후 오름차순을 검증
- 힙 정렬: 입력 배열 자체를 최대 힙으로 사용(별도 힙 배열 없음). 배열을 최대 힙으로 구성(아래에서 위로 `sift_down`)한 뒤, 루트와 마지막 원소를 교환하고 힙 크기를 줄여 `sift_down`으로 힙 속성을 복구하는 과정을 반복합니다. 반복문으로 구현했습니다.
- 병합 정렬, 퀵 정렬: 과제 13과 같은 구현(퀵 정렬은 피벗 선택만 다르고 Lomuto 분할은 동일)
- **비교 횟수**
  - 힙 정렬: `sift_down`에서 두 자식 중 큰 값을 고르는 비교와 그 자식을 부모와 비교하는 비교를 힙 구성과 정렬 단계 모두 센다.
  - 병합 정렬: 병합 중 `a[i] <= a[j]` 비교
  - 퀵 정렬: 분할 중 `a[j] < pivot` 비교와 Median-of-Three의 중앙값 결정 비교
  - 반복문 조건, 난수 생성, 데이터 이동은 제외
- **실행시간**: `clock_gettime(CLOCK_MONOTONIC)`로 정렬 함수 호출 전후만 측정하고, 배열 복사와 출력 시간은 제외합니다. 시간이 매우 짧아서 같은 데이터를 200번 정렬한 평균(ms)을 사용합니다.
- **메모리 사용량(추가 메모리)**: 원본 배열은 제외하고 다음을 더합니다.
  1. 임시 배열: 병합 정렬은 `n × sizeof(int) = 4n` Byte를 직접 계산합니다. 힙 정렬과 퀵 정렬은 임시 배열이 없어 0입니다.
  2. 호출 스택: 재귀 함수(병합, 퀵)와 `sift_down`/`heap_sort`가 호출될 때 지역 변수의 주소를 읽어 가장 깊이 내려갔을 때의 주소를 기록하고, 시작 주소와의 차이를 최대 스택 사용량(Byte)으로 사용합니다. 힙 정렬은 반복문 구현이라 호출 깊이가 일정하고 보조 변수(인덱스, 크기 등)만 쓰므로 이 값이 곧 보조 변수와 호출 스택의 합입니다. 별도의 한 번의 실행에서만 측정하여 시간 측정에 영향을 주지 않습니다.
  - 한계: 측정 시작 주소와 첫 호출 사이의 고정 크기 프레임(`main`, `run` 등 수십 Byte)이 모든 값에 포함되고, 맨 아래에서 호출되는 `partition`/`merge`의 프레임은 포함되지 않습니다. 프레임 크기는 컴파일러와 최적화 옵션에 따라 달라집니다.

## 분석

### 1. 비교 횟수
네 알고리즘 모두 n이 2배가 될 때 비교 횟수가 2배보다 약간 더 늘어 O(n log n)과 일치합니다. 비교 횟수는 병합 < 퀵 < 힙 순으로 적었고, 힙 정렬이 병합 정렬의 약 1.96배(n=20,000), 퀵 정렬(First)의 약 1.56배였습니다. n log₂n(n=20,000에서 약 285,754)과 비교하면 병합 정렬은 약 0.91배, 퀵 정렬은 약 1.1~1.2배, 힙 정렬은 약 1.8배입니다.

- 힙 정렬은 `sift_down`이 한 층을 내려갈 때마다 비교를 2번(두 자식끼리, 큰 자식과 부모) 하고, 정렬 단계에서 n번의 원소 추출마다 힙 높이 log₂n 근처까지 내려가므로 약 2n log₂n에 가까운 비교가 필요합니다. 마지막 원소를 루트로 옮겨 놓고 내리기 때문에 대부분 맨 아래까지 내려가는 점도 비교가 늘어나는 원인입니다.
- 병합 정렬은 항상 절반으로 나누어 깊이가 log₂n으로 고정되고, 병합 한 번에 최대 (길이−1)번만 비교하여 가장 적습니다.
- 퀵 정렬은 분할이 완벽히 반으로 나뉘지 않아 평균 약 1.39 n log₂n까지 늘어나지만 분할당 비교가 1번이라 힙 정렬보다 적습니다.

### 2. 실행시간
n=20,000에서 퀵(First) 1.45 ms < 퀵(Median3) 1.54 ms < 퀵(Random) 1.70 ms < 병합 1.87 ms < 힙 1.95 ms 순이었습니다.

- 힙 정렬은 가장 느렸습니다. 비교 횟수는 병합 정렬의 약 2배였지만 시간은 약 1.05배 정도만 더 걸려, 비교 횟수 차이가 시간 차이로 그대로 나타나지는 않았습니다. 병합 정렬은 비교가 적은 대신 임시 배열에 쓰고 다시 복사하는 데이터 이동 비용이 크기 때문입니다. 반면 힙 정렬은 부모와 자식 사이를 `i → 2i+1`처럼 크게 건너뛰며 접근하므로 캐시 효율이 낮고, 비교 결과에 따라 분기가 달라져 예측이 어렵습니다.
- 퀵 정렬은 제자리에서 배열을 순차적으로 훑으며 교환해 캐시 효율이 좋아 비교 횟수가 병합 정렬보다 많아도 더 빨랐습니다.
- 작은 n(1,000)에서는 힙과 병합이 비슷했고(0.038 ms), n이 커질수록 힙이 조금씩 뒤처졌습니다.

### 3. 메모리 사용량
- 힙 정렬은 입력 배열 자체를 힙으로 사용하고 반복문으로 구현해 n과 관계없이 200 Byte로 일정했습니다(보조 변수와 몇 개의 호출 프레임).
- 병합 정렬은 임시 배열 4n Byte가 필요해 n에 비례해 늘어났고(1,000 → 5,048 Byte, 20,000 → 81,448 Byte), 세 알고리즘 중 가장 컸습니다.
- 퀵 정렬은 임시 배열은 없고 재귀 스택만 써서 1.5~3 KB이며 n이 20배가 되어도 2배 안쪽으로만 늘었습니다(재귀 깊이가 평균 O(log n)). Median3의 스택이 First나 Random보다 작은 것은 분할이 더 균형 잡혀 재귀 깊이가 얕았기 때문입니다.

### 4. 퀵 정렬의 피벗 선택 방법에 따른 차이
Median3는 n=2,000 이상에서 비교 횟수가 가장 적었습니다. 세 값의 중앙값은 극단값일 가능성이 낮아 분할이 더 균형 잡히기 때문입니다. n=1,000에서는 중앙값 결정에 드는 추가 비교(분할당 2~3회)의 비중이 커서 가장 많았습니다. Random은 First보다 대체로 적었으나(20,000 제외) 차이가 작았고, 무작위 데이터에서는 두 방법의 분할 균형이 통계적으로 같습니다. 이미 정렬된 입력에서는 First가 O(n²)으로 나빠지지만 Random과 Median3는 영향이 작습니다. 실행시간은 First와 Median3가 비슷했고, Random은 분할마다 `rand()`를 호출하는 비용(비교 횟수에는 포함되지 않음) 때문에 더 느렸습니다.

### 5. 시간 복잡도와 공간 복잡도

| 알고리즘 | 시간(평균) | 시간(최악) | 공간 |
|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(1) |
| 병합 정렬 | O(n log n) | O(n log n) | O(n) (임시 배열) |
| 퀵 정렬 | O(n log n) | O(n²) | O(log n) 평균, 최악 O(n) (재귀 스택) |
세 알고리즘의 평균 시간 복잡도는 같지만 상수 계수와 메모리 접근 방식 때문에 실제 성능은 달랐습니다. 퀵 정렬은 평균적으로 가장 빠르고 메모리도 적지만 최악의 경우가 있고, 병합 정렬은 비교 횟수가 가장 적고 성능이 안정적이지만 추가 메모리를 많이 쓰며, 힙 정렬은 최악의 경우에도 O(n log n)이 보장되고 추가 메모리가 거의 필요 없는 대신 비교 횟수가 가장 많고 이번 실험에서 가장 느렸습니다.
